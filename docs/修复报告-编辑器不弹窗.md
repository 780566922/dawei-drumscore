# APLAY 修复报告：插件能被找到，但打开没有界面

日期：2026-10-07　版本：1.0.0（构建号 2）

---

## 结论

上一轮的分类字符串修复生效了 —— MuseScore 现在能发现 APLAY。
但「点开没界面」是**另外两个独立 bug**，都已修复并重新安装：

1. `isPlatformTypeSupported` 匹配了一个**在 VST3 规范里根本不存在的常量**（主因）
2. 控制器的音频后端指针**从头到尾没有被赋值**（隐蔽，会导致弹出来的窗口是空壳甚至崩溃）

---

## 根因 1：平台类型字符串写错了

宿主打开编辑器的第一件事是问插件：「我能把你放进 NSView 吗？」

```cpp
// 修复前
if (type && std::string(type) == "PLATFORM_UI") return kResultOk;
return kNotImplemented;
```

`"PLATFORM_UI"` 是自造的值。规范里的真实常量（`pluginterfaces/gui/iplugview.h`）：

| 常量 | 字符串值 | 平台 |
|---|---|---|
| `kPlatformTypeNSView` | `"NSView"` | **macOS —— MuseScore 问的就是它** |
| `kPlatformTypeHWND` | `"HWND"` | Windows |
| `kPlatformTypeHIView` | `"HIView"` | macOS 旧宿主 |
| `kPlatformTypeX11EmbedWindowID` | `"X11EmbedWindowID"` | Linux |

我们答「不支持」→ MuseScore 判定插件没有原生编辑器 → **静默不弹窗，连报错都没有**。

**修复**：按平台匹配真实常量，不支持时返回 `kResultFalse`。

---

## 根因 2：控制器拿不到音频处理器

VST3 里**处理器和控制器是两个独立的对象实例**，控制器不会自动持有处理器的指针。

全项目搜索发现 `setBackend()` 唯一的调用点在已废弃、不参与编译的 `plugin.mm` 里，
主线上 `m_backend` 恒为 `nullptr`。后果：

- 拖文件没反应、滑块不动（所有操作都打在空指针路径上）
- 定时刷新播放头的 `tick` 里 `_st->backend->hasAudio()` 会**直接崩溃**

**修复**：两条路径都实现

| 路径 | 做法 |
|---|---|
| 规范路径 | 重写 `controller->connect(IConnectionPoint*)`，对端就是处理器；用 `queryInterface(IAudioProcessor::iid)` 取出后 `dynamic_cast` 转回来 |
| 兜底路径 | 处理器构造时把自己登记进 `static std::atomic<APlayProcessor*>`，控制器直接取最近实例（覆盖宿主没建连接点、或连接晚于 createView 的情况） |

另外给视图加了「挂载时再解析一次后端」的机制，解决时序竞争。

---

## 顺手加固

宿主在后端注入**之前**就打开编辑器做探测，是合法行为。与其在界面代码的
20 处调用点逐个判空，不如保证指针永不为 null —— 加了一个 `NullBackend`，
所有方法返回安全的空值。定时器再也不会因为后端未就绪而崩溃。

---

## 验证结果

构建脚本自动跑的验证器，从 63 项增加到 **66 项，全部通过**：

```
[PASS] 扫描阶段 createView 返回非空（无后端时）
[PASS] isPlatformTypeSupported("NSView") 为真（macOS 宿主实际问这个）
[PASS] isPlatformTypeSupported("PLATFORM_UI") 必须被拒绝（防回归）
[PASS] createView 返回视图
[PASS] 视图已绑定音频后端（界面按钮真实有效）
```

其中第 2、3 项是**锁死错误常量**的防回归断言 —— 以后再改到别的字符串会立刻失败。

另外双架构（x86_64 + arm64）校验通过，三个必需导出符号 `GetPluginFactory` /
`bundleEntry` / `bundleExit` 齐全，真实音频渲染验证通过（峰值 0.0858）。
