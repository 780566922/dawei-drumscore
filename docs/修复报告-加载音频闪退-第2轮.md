# 修复报告：载入音频闪退（第 2 轮）

## 一句话结论

这次的崩因**不是解码**，而是**对象生命周期**：视图缓存了音频处理器的**裸指针**，
宿主销毁处理器后视图仍在使用 → 野指针 → 闪退。

同时给插件装了**崩溃取证**：万一还有下次，`~/Library/Logs/APLAY.log` 会直接写出
信号类型和调用栈，不用再靠推理。

## 改了什么

### 1（主因）视图不再持有处理器的裸指针

原来的机制是这样：处理器构造时把自己记在一个静态变量里（"最近实例"），
控制器和视图把这个**裸指针**缓存下来用。

问题在于：**VST3 里处理器和编辑器视图的生命周期没有从属关系**。
宿主完全可以先销毁处理器（关音频引擎），而视图和它的 20Hz 刷新定时器还活着。
那一刻，定时器和"打开音频"按钮就打在**已释放的内存**上——正好就是
"一操作就闪退"。

**改成**：视图只拿一个**进程级永生的代理对象**（地址恒定）。代理内部通过注册表
解析"当前活跃的处理器"，处理器析构时自动注销。没有处理器时，所有调用返回
安全默认值（无音频、不播放），**而不是崩溃**。

### 2 解码路径整体换短

旧的解码是"AVAudioFile + 手工 AVAudioConverter 转 interleaved float32"。
这条路上发现一个真实缺陷：`convertToBuffer` 的输入回调是**值捕获**，
导致每次回调都声称"还有数据"，把同一个缓冲**反复投喂**给转换器。
另外 AVAudioConverter 在个别格式组合下会抛 ObjC 异常，而插件里没人接。

**改成** `AVAudioFile initForReading:commonFormat:interleaved:error:`——让它
直接把文件以 float32 读出来。压缩格式解码、位深转换全在系统框架内部完成，
我们只做"非交错 → 交错"。代码路径更短，异常面更小，并且整个过程套了
`@try`，任何异常都转成"载入失败"提示，**绝不让它穿出去把宿主带走**。

### 3 顺手修掉的三个真实缺陷

- **`dealloc` 漏了 `[super dealloc]`**（两处）：MRC 下不调它，NSView 自己的
  资源（子视图、图层）不会被释放，每次开关编辑器都在漏。
- **宿主采样率的跨线程读写**：宿主线程写、音频线程读，是真实的数据竞争
  → 改成原子量。
- **音频解码文件用的是 MRC 且从不 release**：每次载入泄漏一批
  `AVAudioFile` / `PCMBuffer` → 改用 ARC。

## 装了取证：下次不用再猜

`source/crashguard.mm` 在插件加载时安装三类处理器：

- ObjC 未捕获异常
- `std::terminate`（未捕获的 C++ 异常）
- 信号（SIGSEGV / SIGABRT / SIGBUS / SIGILL / SIGFPE）

任何一类发生，都会把**类型 + 调用栈**写进：

```
~/Library/Logs/APLAY.log
```

载入流程的每个阶段也埋了点（载入请求 → 开始解码 → 解码完成 → 音频就绪），
所以日志里会清楚看到**最后走到了哪一步**。
